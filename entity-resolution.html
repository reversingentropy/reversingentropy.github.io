The Problem

17 trillion comparisons. One laptop. No GPU cluster.

Authority control is unglamorous infrastructure work. NLB maintains personal name authority records - people, organisations, geographic entities - that need to align with the Library of Congress Name Authority Files (LCNAF) as the canonical external reference. When they don't, the same person appears under multiple inconsistent forms across NLB's systems, breaking entity linkage and degrading discovery quality downstream.

The data problems are exactly what you'd expect at this scale: typos, outdated labels, missing identifiers, inconsistent transliterations, diacritics. "Carpelan, Bo Gustaf Bertelsson, 1926-" vs "Carpelan, Bo, 1926-2011." "Kim, Young-Hee: Sculptor" vs "Kim, Young-Hee: Chef." These aren't edge cases - they're everywhere.

The hard constraint: a single laptop, 64GB RAM, no GPU cluster. Every architectural decision flowed from this.

Naive O(n×m) matching across 1.45M records against 12M LCNAF records produces 17 trillion pairwise comparisons. The problem isn't finding the right algorithm - it's making the problem tractable at all.

Design principle

Start with the cheapest method. Only add complexity for what's left. Scalable, layered design beats both brute-force and overengineered approaches.

The Approach

Three phases, each earning its existence

The solution is a staged pipeline where each phase handles the easiest remaining cases and passes only the genuinely hard ones downstream. The goal is to never run an expensive method on a problem a cheap one can solve.

01
Deterministic SQL joins

Load LCNAF (via SPARQL from GraphDB → CSV) and ILS records into PostgreSQL. Inner-join on LC Control Numbers (LCCN) - records with matching identifiers link instantly. Then label normalisation: lowercase, strip punctuation. Simple but surprisingly effective. LCCN join: 25% matched. Label normalisation: +23%. Total: 48% of 1.45M records resolved before any ML. SQL chosen deliberately over GraphDB (memory-intensive for bulk text ops) and Excel (hard cap at ~1M rows).

02
Blocking + string matching

For the remaining 511K records, ran a proper blocking algorithm selection process - evaluated q-gram, standard, extended q-gram, suffix arrays, and extended suffix arrays against recall and comparison reduction ratio. Selected trigram blocking to reduce candidate pairs by over 90%, followed by string similarity (Levenshtein, Jaro, Jaccard) with threshold optimisation. Trained and evaluated on 34,175 labelled name pairs with LCCN ground truth. Test F1 ≈ 98.85%. The method worked. The scale didn't.

Trigram blocking Levenshtein Jaro Jaccard
Dead end

Blocking methods broke down at 1.45M records. Too many candidate pairs generated. Token-based methods consumed excessive memory. Intermediate data structures grew faster than available RAM. 98.85% F1 on the labelled test set - but unrunnable in production on a single laptop. The algorithm was sound. The hardware constraint killed it. Time to rethink.

03
Text embeddings + approximate nearest neighbour search

The insight from Phase II: string matching requires generating and comparing candidate pairs explicitly. Embedding-based search doesn't - encode once, then search an index. Benchmarked five embedding models on accuracy, encode speed, and RAM usage. Selected MiniLM-L6 as the best efficiency/accuracy balance (~1,266 MB RAM on test set). Built an IVFFlat index (k-means into Voronoi cells, tuned nlist and nprobe) to retrieve top-10 candidates per query without exhaustive search. Re-ranked the top-10 using an XGBoost classifier trained on string and embedding similarity features - using the high-confidence LCCN matches from Phase I as ground truth, with no manual annotation needed. ANN makes the 511K × 12M search tractable; XGBoost makes the final call precisely.

MiniLM-L6 IVFFlat FAISS XGBoost
Why XGBoost for reranking

The LCCN-matched records from Phase I gave clean ground truth for free - no manual annotation needed. XGBoost on string and embedding similarity features trains fast, handles mixed feature types, and is interpretable. When a cataloguer questions a match decision, you can show them which features drove it. "The neural network said so" is not a defensible answer in a production library system.

Outcome

1.2M+ records matched. 8-year backlog retired.

Honest reflection

What I'd do differently

Phase II failing at scale was the most instructive moment. The blocking methods were correct - the test results proved that. The mistake was not running a smaller-scale test (say, 100K records) before committing the full dataset. That would have caught the memory ceiling earlier and saved significant time.

MiniLM-L6 was a reasonable choice given that ILS preferred names are stored in English, so the matching problem was largely English-to-English. The issue is that LCNAF contains multilingual variants - alternate labels in Chinese, Malay, Tamil and other scripts - and MiniLM-L6 doesn't handle those well. In practice this means the pipeline matches on preferred English forms but misses connections that could have been made via non-Latin alternate labels. A multilingual embedding model would have captured those at modest additional cost. Not a critical flaw for the core use case, but a real gap in coverage.

The XGBoost reranker was trained on LCCN-derived ground truth, which skews Western. The same distribution mismatch applies. A few thousand Southeast Asian name pairs, manually verified, would likely improve final F1 more than any model upgrade. Data quality beats model sophistication here.
