The Problem

A recommender that can only see what's in the metadata

Singapore Infopedia is NLB's digital encyclopedia - articles covering the country's history, culture, prominent personalities, and significant events. Each article is accessible via National Library Online and includes a Sidebar: a recommender engine that surfaces related resources from NLB's broader collection.

The Sidebar works by traversing relationships in NLB's Linked Data Knowledge Graph. An article about dragon dance connects to resources about Chinese cultural associations, specific events, geographic locations. But those connections only exist if the entities are in the metadata. Most aren't - they're mentioned in the article text but never formally linked.

Manual entity tagging across 1,880 articles was not happening at meaningful speed. The question was whether GPT-4 could extract Singaporean entities from article text accurately enough to add directly to the knowledge graph, with a strong preference for precision over recall - a wrong connection in the KG is worse than a missed one.

The precision trade-off

If an article about dragon dance mentions 5 entities, and we're only certain about 2, we add 2. Not 5. Missed entities are a gap in coverage. Wrong entities corrupt the graph and mislead the recommender. The decision to optimise precision over recall was deliberate and consequential throughout the design.

The Approach

Two stages: extract, then match

The pipeline has a clean separation between extraction and linking. GPT-4 does the extraction - identifying what's in the text. String matching does the linking - connecting extracted entities to what's already in the knowledge graph. These are different problems and they need different tools.

01
Entity extraction with Chain-of-Thought prompting

A Chain-of-Thought prompt guides GPT-4 through a structured process: read the text, identify candidate entities, classify each as Person/Place/Organization, provide reasoning for each classification, output structured JSON. The CoT structure is important - it forces the model to reason explicitly before classifying, which reduces hallucinations and improves adherence to the entity type definitions. Focus is strictly on Singaporean entities - non-fictional people, geographic locations, and organisations relevant to Singapore's context. The reasoning step also surfaces false positives: "Jade Emperor" is a deity, not a person; "National Day" is an event, not an organisation.

02
Entity matching against NLB Named Authorities

Extracted entities are matched against the NLB Named Authorities Dataset - standardised names crucial to Singapore's politics, economy, society, culture, and history. Two preprocessing steps before matching: qualifier removal (stripping date qualifiers and role descriptors from entity names to focus on core names) and alternate name resolution (all alternate and preferred labels resolve to a single preferred entity through a directed graph - so "LKY", "Mr. Lee", and "Lee Kuan Yew" all route to the same node). String matching then produces three possible outcomes.

What was considered and rejected

Automated entity resolution was explicitly evaluated and not deployed. The risk of false positives - unrelated records mistakenly linked - was judged to outweigh the efficiency gain at this stage. This is the same problem the entity resolution pipeline addresses at scale. Here, with a knowledge graph serving a public recommender, caution won.

Outcome

Precision of 0.975. One hallucination in 100 articles.

Evaluation was conducted on 100 Singapore Infopedia articles. GPT-4 produced 2,066 true positives and 52 false positives - a precision of 0.975. There was one hallucination: an entity that was contextually plausible but not explicitly mentioned in the article text. False negatives (entities missed by the model) were not the primary evaluation focus, consistent with the precision-first design philosophy.

Non-reproducibility risk
Real

The same prompt on the same text on a different day can produce different results. This is documented in the paper as a genuine operational constraint for library systems.

Honest reflection

What the paper documents and what I'd add

The precision result is strong but the dataset is small - 100 articles out of 1,880 is not a large evaluation set. Generalisation to the full collection, particularly articles covering topics with more ambiguous entity boundaries, is an open question. The paper is clear about this.

The non-reproducibility problem is more serious than it sounds for a production library system. Metadata that changes depending on when you run the pipeline isn't metadata you can rely on for a public recommender. The longer-term answer is probably a deterministic NER model fine-tuned on Singapore-specific entity data, rather than a generative model - more predictable, more auditable, cheaper to run at scale. GPT-4 was the right tool for exploration and initial population of the graph. It may not be the right tool for ongoing maintenance.

There's also a data flywheel opportunity here that wasn't explored: the entities extracted and verified in this project are now ground truth training data for a future fine-tuned model. The work done here seeds the next phase, if someone picks it up.
